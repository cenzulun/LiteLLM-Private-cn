# 源采集监控

1.0.13 增加引擎、设备和网关 `/metrics` 的源采集。Prometheus 配置、查询和告警入口保留，两类指标分别展示，不合并相加。

## 页面配置

打开推理监控、引擎与昇腾资源或智能路由页面中的“配置源采集”，新增采集源。

| 配置 | 填写说明 |
| --- | --- |
| 采集名称 | 自定义名称，区分同模型不同副本 |
| 完整指标地址 | 网关容器可访问的 `http://实例:端口/metrics`，不是推理基础地址 `/v1` |
| API Key | 指标接口实际使用的密钥，以 `Authorization: Bearer` 发送。无鉴权可留空 |
| 关联模型部署 | 选择平台登记的独立模型部署。只监控可以留空，用于路由时必须绑定 |
| 模型标签过滤 | 多模型指标接口可填写 `model_name` 标签原值 |
| 采集周期 | 默认十秒，支持五到三百秒 |
| 连接超时 | 默认五秒，支持二到二十秒 |
| 证书验证 | 默认开启，HTTPS 应安装受信任的内网证书 |
| 站内告警阈值 | 排队请求数、缓存占用率和首令牌时延九十五分位，可按模型调整 |

“测试指标连接”只测试，不保存配置与历史。“保存采集配置”后后台持续运行，关闭浏览器不停止采集。编辑已保存采集源时密钥留空保留原值，勾选清除才移除。接口不会返回密钥原文或密文。

企业自用地址段不会按公私网分类阻止，地址仍需为合法的 HTTP/HTTPS 地址，不能嵌入账号密码、查询参数或片段。禁止自动跟随重定向，避免密钥被转发到其他服务。

## 统计口径

| 面板指标 | 对应引擎指标 |
| --- | --- |
| 运行、排队请求数 | `vllm:num_requests_running`、`vllm:num_requests_waiting` |
| 输入、输出令牌累计与速率 | `vllm:prompt_tokens_total`、`vllm:generation_tokens_total` |
| 每秒完成请求数 | `vllm:request_success_total` |
| 首令牌时延 | `vllm:time_to_first_token_seconds` 直方图 |
| 排队时延 | `vllm:request_queue_time_seconds` 直方图 |
| 端到端时延 | `vllm:e2e_request_latency_seconds` 直方图 |
| 缓存占用率 | `vllm:kv_cache_usage_perc`，兼容旧版 `vllm:gpu_cache_usage_perc` |
| 前缀缓存命中率 | `vllm:prefix_cache_hits_total` / `vllm:prefix_cache_queries_total` |
| 推测解码接受率 | `vllm:spec_decode_num_accepted_tokens_total` / `vllm:spec_decode_num_draft_tokens_total` |

前三类速率使用连续采样的增量；时延同时提供累计平均值、窗口平均值和窗口第九十五／九十九分位。不同版本未暴露的指标不会生成数值。排队原因、缓存配置、逐设备标签以及其他未预置汇总的指标可从“查看原始指标与标签”查询；未预置汇总指标暂不提供长期趋势。

- 当前值包括运行请求、排队请求、缓存占用以及进程资源。
- 输入输出令牌、完成请求、前缀缓存、推测解码等累计值是该引擎当前暴露的进程累计，包含绕过网关的流量，不等同于网关账号用量。
- 速率由最近五分钟内最早有效采样与当前采样的计数差除以时间差计算。刚启用时逐步积累窗口，未生成足够采样时显示暂无数据。
- 时延平均值同时提供进程累计和采样窗口口径。九十五、九十九分位由窗口直方图桶增量插值估算。空闲窗口显示无新增样本，不借用累计值作为实时分位数。
- 引擎重启、计数下降或序列变化时不生成负速率，重新积累窗口。不同桶边界的直方图不伪造合并分位数。
- 原始指标入口保留数值、名称和标签，包括未预置专属面板的扩展指标，支持搜索与分页。指标接口没有提供的设备利用率等内容不会补造。
- 昇腾计算卡利用率、显存、功耗和温度需要单独接入设备导出器。进程内存不等同于昇腾显存。

采集失败、超时、鉴权异常或样本超过三个采集周期且至少三十秒未更新时，将标为异常或过期。最后成功数值可查看，但不作为新鲜路由压力。

## 路由与告警

开启“将源采集的运行与排队压力用于实例选择”，并在路由策略中使用历史时延路由。平台先从健康部署中选择，优先使用运行数与排队数较低的副本。一个独立模型部署只允许绑定一个启用的引擎采集源；无新鲜数据、多模型标签不唯一或未绑定时回退到历史时延。源采集压力开启后优先使用该来源，不将其与 Prometheus 压力相加。

采集异常和阈值超限在页面显示活动告警。尚未实现告警通知推送或历史告警归档。Prometheus 活动告警仍通过原入口查看。

## 持久化与规模

采集配置与加密密钥保存在现有 PostgreSQL 的平台配置记录。密钥以固定 `LITELLM_SALT_KEY` 派生的密钥加密，升级和恢复必须保留该盐值。

趋势与原始基线保存在原有 `motor_module_state` 持久化卷中的 `direct-monitor.sqlite3`，不依赖调度服务进程。SQLite 原子采集租约防止同机多网关进程重复采集，默认四路并发。指标响应限制四兆字节、一万条数值序列，防止异常采集耗尽资源。

历史默认保留七天，可设一到三十天；全库最多二十五万条采样，先达到任一上限即淘汰旧数据。例如十四个实例十秒采一次时，总量上限约可保存两天。实际磁盘占用取决于指标数量，需按现场容量调整方案。原始基线保留约十分钟，完整原始指标只保留最近成功采样；面板历史保存汇总数值。

同一宿主机双进程共用采集锁与历史。多宿主机网关不能靠各自本地 SQLite 卷自动协调采集和集中历史，需保留 Prometheus 或另行部署集中采集存储。本版适用于当前 Compose 单机网关部署。

## 升级

沿用原 Compose 项目名、`.env`、数据库和持久化卷，将网关镜像更新到 `realai/gateway:1.0.13-arm64`。新状态文件自动创建，不需要重新初始化，不覆盖已有模型或监控配置。旧的 Prometheus 配置继续有效。单网关容器更新会短暂中断访问。

用户提供的采样仅用于本机回放验证，不包含在源码或离线包中。演示与测试采集源在验证结束后清理，不冒充在线生产数据。
